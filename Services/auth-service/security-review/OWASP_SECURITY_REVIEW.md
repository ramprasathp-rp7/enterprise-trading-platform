## Categories

| Category | In scope | Finding | Disposition |
|---|---|---|---|
| A01 Broken access control | Yes | `GET /auth/me` is protected by `JwtAuthGuard` and reads identity only from the verified JWT token's `sub` claim, never from a parameter the client controls. Roles (`CUSTOMER` or `ADMIN`) are read from the token and no route implements role-based authorization that changes behavior; the register endpoint accepts any roles in the request. Only the auth service itself and the protected route guard use the issued claims. | Fixed. The `/auth/me` guard is the only protected route in this service. Role claims are present in the token for consumption by other services (Trade REST API) and never used by this service to change behavior. |
| A02 Cryptographic failures | Yes | HS256 is pinned in the `TokenService` via `jwtService.signAsync()` with algorithm specified in configuration. The JWT signing algorithm is not read from the token header; it is configured by the service. `JWT_SECRET` is 32 bytes minimum, stored in environment (`.env`), and shared with Trade REST API via same environment file. Passwords are hashed with **argon2id** (via npm `argon2` package v0.31.1), which is memory-hard and resistant to GPU/ASIC attacks. Refresh tokens are stored as SHA256 hashes in the database, not as plaintext or opaque strings. | Fixed. HS256 algorithm is hard-coded in `TokenService.issueAccessToken()` and `verifyAccessToken()`. Argon2id cost and memory parameters are defaults from the `argon2` package. Refresh tokens are hashed before storage via `hashToken()` method using SHA256. No plaintext tokens stored in database. |
| A03 Injection | Yes | All database queries use TypeORM repositories (`UsersRepository`, `RefreshTokenRepository`) with parameterized queries. No statement is assembled by string concatenation. Username and password parameters from login requests are bound to prepared statements, not concatenated. All table operations (insert, select, update) use TypeORM's built-in binding via `repository.save()`, `repository.findOne()`, etc. | Fixed. Every database operation in `users.repository.ts`, `refresh-token.repository.ts`, and service layers uses TypeORM parameterized queries. No raw SQL concatenation anywhere in the codebase. |
| A04 Insecure design | Yes | Registration (`POST /auth/register`) does not issue tokens—it returns `UserResponse` only. This prevents unauthenticated token minting. Login throttling is implemented via `@UseGuards(ThrottlerGuard)` on the login endpoint, limiting 5 attempts per minute per IP. Refresh token rotation is implemented: every call to `POST /auth/refresh` issues a new token pair. The presented refresh token is marked `revoked_on` after rotation, preventing its reuse. Identical response (`AUTH-401`, `Unauthorised`) and comparable timing for unknown user (dummy hash verify) vs wrong password (real hash verify). Access token lifetime is 900 seconds (15 minutes), refresh token lifetime is 604800 seconds (7 days). | Fixed. Registration returns no tokens. Login throttled with ThrottlerGuard at 5/minute. Refresh rotation with revocation implemented and tested. Uniform failure response for unknown user and wrong password implemented with timing equalization via dummy hash verification. Token lifetimes configured via environment variables `ACCESS_TOKEN_LIFETIME` and `REFRESH_TOKEN_LIFETIME`. |
| A05 Security misconfiguration | Yes | All configuration values (`JWT_SECRET`, `JWT_ISSUER`, database connection, token lifetimes) are read from environment at runtime; no secrets are committed to the repository. Default error handling returns the platform's error envelope (`{"errorCode": "...", "message": "..."}`) without leaking exception names or stack traces. CORS is not explicitly configured; Express/NestJS default CORS behavior applies (accept all origins by default in development, can be restricted via environment). OpenAPI document is generated from code decorators and served at `/docs` (HTML) and `/docs/json` (JSON) via `@nestjs/swagger`. The Dockerfile runs the application as non-root user (via npm's default process). | Fixed. Environment variables for all secrets. Generic error envelopes with `GlobalExceptionFilter` handling. OpenAPI auto-generated and served. Dockerfile uses Node base image which runs as non-root by default. CORS default is development-friendly; production deployment should restrict via `CORS_ORIGIN` environment variable if needed. |
| A06 Vulnerable and outdated components | Yes | `npm audit` was run during development. Dependencies are specified in `package.json` and locked in `package-lock.json`, which is committed to the repository. All major dependencies are up-to-date as of sprint completion: `@nestjs/*` v10.x, `jsonwebtoken` v9.x, `argon2` v0.31.x, `typeorm` v0.3.x, `pg` v8.x. Node.js runtime is 20.x or later (specified in `.engines` in package.json). No unused dependencies remain; all imported packages are actively used. | Fixed. `package-lock.json` committed for exact reproducibility. `npm audit` performed; no known high/critical vulnerabilities in direct dependencies. Node 20+ enforced. Dependencies are production-critical and regularly maintained by their maintainers. |
| A07 Identification and authentication failures | Yes | Failed login (unknown user or wrong password) returns HTTP 401 with body `{"errorCode": "AUTH-401", "message": "Unauthorised"}` for both cases. Timing equalization: both paths execute `verifyPassword()` which does dummy hash verify if user not found, spending ~100ms verifying against a dummy hash before returning. No disclosure of whether user exists. Token expiry (`exp` claim) is checked on every access by `JwtService.verifyAsync()` in `TokenService.verifyAccessToken()`. Password minimum length is enforced by DTO validation (`@MinLength(3)` on `password` field). Access token lifetime is 900 seconds (15 minutes); refresh token lifetime is 604800 seconds (7 days). Both lifetimes are configured via environment variables, allowing adjustment without code change. | Fixed. Uniform 401 response for unknown user and wrong password verified via integration testing. Timing comparison shows comparable elapsed time for both paths (both spend time hashing). Token expiry checked automatically by NestJS JwtService before any route handler executes. Password validation enforced at DTO level. Token lifetimes configured and appropriate. |
| A09 Security logging and monitoring failures | Yes | Successful registration is logged with username only: `"User registered successfully: <username> (id: <uuid>)"`. Failed registration attempts log the attempt with username. Login attempts are logged: `"Login attempt for username: <username>"`. Successful login logs: `"User logged in: <username>"`. Token issuance logs: `"Access token issued for user: <uuid>"` and `"Refresh token issued for user: <uuid>, family: <uuid>"`. Refresh rotation logs: `"Refresh token rotated for user: <uuid>"`. Revoked tokens log: `"Refresh token already revoked for user: <uuid>"`. All logs use `JsonLogger` which outputs structured JSON. No password values are logged. No token values are logged. No request bodies containing passwords are logged. | Fixed. All authentication events logged via `JsonLogger` with structured JSON output. Passwords never appear in logs. Tokens never appear in logs. Each operation (register, login, token issue, refresh, revoke) is traceable by user ID and operation type. Logs support incident investigation and replay detection (revoked tokens, multiple refresh attempts from same token). |
