# 0031 Platform configuration is centralized in Config/application.yaml

| Field | Value |
|---|---|
| Status | accepted |
| Date | 2026-10-08 |
| Decided by | Sahajanya |

## Context

Each microservice (auth-service, order-service, executor-service) and the Angular frontend had hardcoded default ports and database connection strings scattered across multiple configuration files:
- `Services/auth-service/src/config/configuration.service.ts`
- `Frontend/trading-ui/src/app/core/config/environment.ts`
- Individual service `application.properties` files
- Test configuration files with separate port numbers

When running the full platform locally (frontend + 3+ services + Kafka + PostgreSQL), developers had to manually coordinate which ports were in use across different files. Changes to the port mapping required updates in multiple places. The API contracts in `Frontend/trading-ui/contracts/` also hardcoded service URLs and ports.

Additionally, the frontend's `environment.ts` file had conditional imports based on build mode, making it difficult to change service URLs without rebuilding the entire application.

## Options considered

| Option | For | Against |
|---|---|---|
| Keep hardcoded defaults in each service | Simple, no central dependency, services are independent | Duplicated configuration across 5+ files, difficult to coordinate port changes, frontend must rebuild to change service URLs, no single source of truth |
| Environment variables only | Well-understood, platform-agnostic, works in containers | Requires listing all variables in documentation, developers must know which variables to set, no validation of compatibility, hard to see the full platform topology |
| Centralized YAML file with fallbacks to env vars and defaults | Single source of truth, readable platform topology, backward compatible with env vars and hardcoded defaults, services validate against the file at startup, can be version-controlled, easier to document | Requires a new file and tooling to read it, adds one dependency (YAML parser), the YAML must be present during development (but can be regenerated) |

## Decision

Create `Config/application.yaml` as the single source of truth for platform-wide configuration (frontend port, service URLs, database connection). Each service reads this file at startup with a fallback chain:
1. Environment variables (highest priority, for container/CI overrides)
2. `Config/application.yaml` values (the canonical topology for development)
3. Hardcoded defaults (lowest priority, for services run in isolation)

The auth-service loads the config via `loadPlatformConfig()` in `src/config/platform-config.ts`. The frontend uses a pre-build script `scripts/sync-platform-config.mjs` that generates `src/app/core/config/platform-config.generated.ts` from the YAML before every `npm start`, `npm run build`, or test run. The generated file is committed to git so builds work without the script or YAML (e.g., in CI/CD).

What decided it is that the frontend must know the service URLs at build time (they are imported as constants in feature services), but those URLs should not be rebuilt into different binaries for different environments. The YAML file can be regenerated by the platform operator before building, and the generated TypeScript reflects the current topology.

## Consequences

- **Single topology source**: `Config/application.yaml` now lists every service port and the database connection. Changing the platform topology (e.g., moving order-service to a different port) requires editing one file.
- **Frontend regeneration**: Changes to service URLs require running `npm run sync-config` or `npm start` (which runs the script automatically) before `npm run build` or `ng serve`. The `platform-config.generated.ts` file must be committed after regeneration so CI/CD and other developers have the current topology.
- **Backward compatibility**: Environment variables still override the YAML and defaults, so containerized deployments and CI/CD can set `PLATFORM_CONFIG_PATH=/config/app.yaml` or individual `PG*` variables without changing service code.
- **Database and CORS configuration**: The auth-service now loads `database.host`, `database.port`, `database.name`, and `database.user` from the YAML, not just from env vars. CORS origins are derived from the `frontend.url` and `frontend.port`, so a developer changing the frontend port in the YAML automatically gets the correct CORS setup.
- **Regeneration is required after pulling changes**: If a teammate modifies `Config/application.yaml`, you must run `npm run sync-config` to regenerate `platform-config.generated.ts`. If you skip this, the frontend will not know about the new service URLs and will call the old hardcoded ones from the last build.
- **Trade-off**: The platform is now less modular (each service depends on a file outside its own folder), but far easier to operate locally. A service run in complete isolation (without the YAML file) still works with hardcoded defaults.
- **OpenAPI contracts updated**: All service contracts in `Frontend/trading-ui/contracts/` now reference service URLs read from the platform config instead of hardcoded URLs like `http://localhost:8080`. The generated clients use these URLs from `app.config.ts` providers (e.g., `provideTradeApi(environment.TRADE_API_URL)`).
